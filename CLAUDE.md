# Jarvis — Telegram Spending Tracker

Personal, single-user spending tracker. You (the developer) text purchases to a Telegram bot
("Jarvis"); an LLM parses them and logs to Postgres; the bot replies with confirmation, budget
status, and proactively checks in on spending. No frontend — Telegram is the whole UI.

**Status: all originally-planned phases (1-5) are done and deployed. The project is now in
open-ended feature-extension mode** — most of what's built past Phase 5 came from ad-hoc
requests in chat, not a pre-written spec. Treat this file as the source of truth for what
exists; there is no separate spec doc to reconcile against.

## Stack

- **Messaging**: Telegram Bot API, webhook mode (not polling) — see "How the webhook works" below
- **Compute**: 3 AWS Lambda functions (Python 3.12), `us-east-2`, account `915639745134`
- **API layer**: AWS API Gateway (HTTP API) in front of `jarvis-webhook`
- **DB**: RDS Postgres, instance `jarvis-db`, database `jarvis`
- **LLM**: Claude (`claude-sonnet-5`) via the `anthropic` Python SDK — used for intent
  classification (tool-use, `tool_choice: "auto"`) and free-text generation (going-out check-ins)
- **Scheduling**: Amazon EventBridge Scheduler (not classic EventBridge Rules — needed IANA
  timezone support for DST-safe daily check-in times)

## How the webhook works (mental model, since this tripped up understanding before)

Telegram is registered (via `setWebhook`) to POST every inbound message directly to the API
Gateway URL, in real time. This is a **push** model, not polling — nothing runs continuously
waiting for messages. The chain: **Telegram → API Gateway → Lambda (`jarvis-webhook`)**. The
Anthropic SDK is not what does the "parsing" — it's just the HTTP client. Claude (the model) is
what actually reads the message and decides intent via tool-use; the SDK just carries the
request there and deserializes the JSON response.

## The three Lambda functions

| Function | Trigger | Source | Deploy script |
|---|---|---|---|
| `jarvis-webhook` | API Gateway ← Telegram webhook, every message | `lambda/webhook/handler.py` | `scripts/deploy_webhook.sh` |
| `jarvis-daily-checkin` | EventBridge Scheduler, 3pm & 10pm America/New_York | `lambda/daily_checkin/handler.py` | `scripts/deploy_daily_checkin.sh` |
| `jarvis-session-scheduler` | EventBridge Scheduler, every 15 min | `lambda/session_scheduler/handler.py` | `scripts/deploy_session_scheduler.sh` |

`jarvis-webhook` is the only one that reads what you type — the other two only ever *initiate*
messages to you.

## Deploying changes

After editing a handler:
```bash
./scripts/deploy_webhook.sh            # or deploy_daily_checkin.sh / deploy_session_scheduler.sh
```
After adding a `db/0NN_*.sql` migration:
```bash
./scripts/apply_schema.sh              # replays ALL db/*.sql files in order, every time
```
**Migration idempotency is not automatic** — there's no schema_migrations tracking table, so
every migration re-runs on every deploy. A migration must stay a no-op once superseded by a
later one, not just idempotent against itself. **Always run `apply_schema.sh` twice in a row
after adding a migration** and confirm the second run is clean — that's the actual test. (Hit
this for real: `002_seed_budgets.sql`'s upsert kept resurrecting a stale `food` category row
that collided with `005`'s rename, until both were guarded with `IF NOT EXISTS` checks.)

`.env` holds real secrets (never commit — see `.env.example` for the required keys, all blank).
`.api_gateway_url` is the live invoke URL, gitignored, regenerated by `setup_api_gateway.sh`.

## Data model (6 tables in `jarvis-db`)

- **`transactions`**: id, raw_text, merchant, amount, category, confidence, logged_at,
  session_id (nullable FK)
- **`budgets`**: the **paycheck period** (see below) — category (PK), cycle_limit, cycle_type
  (`semimonthly` | `fixed_days`), cycle_anchor, cycle_length_days
- **`sessions`**: going-out state machine — status `awaiting_target` → `active` → `ended`,
  target_amount, running_total, wind_down_nudge_sent. Partial unique index enforces one
  open (awaiting_target/active) session at a time.
- **`trackers`**: ad-hoc flat $ caps over N hours ("spend $200 in the next 8 hours"),
  independent of sessions/windows, can run concurrently with anything. Progress computed live
  from `transactions.logged_at` falling in the window — no row-tagging.
- **`budget_windows`** + **`budget_window_limits`**: ad-hoc *per-category* budgets over an
  arbitrary duration ("a week", "the weekend"). Status `pending` (setup in progress, mirrors
  sessions' `awaiting_target`) → `active` → `ended`. One open window at a time. Also
  live-computed, not tagged.

## Tracked categories

Only **`food_drink`**, **`groceries`**, **`transport`** are logged/budgeted. Anything else
(shopping, entertainment, etc.) is recognized by the classifier but explicitly **not** logged —
the user gets a "not tracking that category" reply instead. `food_drink` absorbed the original
`coffee` category and covers meals, coffee, and going-out drinks/alcohol.

Display note: the category is stored and matched internally as `food_drink`, but every
user-facing message shows it as **"food/drink"** — see `display_category()` in both
`webhook/handler.py` and `session_scheduler/handler.py`. Don't rename the underlying value;
just keep that display mapping in sync if it's ever touched.

## Two distinct "budget" concepts — don't conflate them

1. **Paycheck period** — the standing, structural budget. Semimonthly (1st-15th, 16th-end of
   month), currently `food_drink $275`, `groceries $250`, `transport $75`. Queried with "how am
   I doing in the paycheck period", adjusted with "reset my transport paycheck limit to X". Has
   **no start/stop/cancel** — it's not a thing the user creates, it's always running.
2. **Budgeting window** — a user-started, arbitrary-duration, per-category budget ("I want to
   start a new budgeting cycle, food and drink 100, groceries 50, transport 30, for the next
   week"). Queried with "how am I doing in my current cycle". Can be cancelled
   (`cancel_budget_window`). Goes through a `pending` state if the user doesn't give everything
   at once — this was a real bug (see below) before that state existed.

A user asking about "my current cycle" (vague) means the budgeting window; "the paycheck
period" (explicit) means the standing one. The tool descriptions in `classify_message` carry
this disambiguation — read them before changing either flow.

## The intent classifier

`classify_message()` in `webhook/handler.py` sends the raw text to Claude with `tool_choice:
"auto"` across a dynamically-built list of ~16 tool definitions (today's date is injected as a
system prompt so relative/absolute dates resolve correctly, e.g. "till October 1st"). Some
tools are only offered conditionally based on current DB state:
- `set_going_out_target` — only when a session is `awaiting_target`
- `add_budget_window_category_limit` — only when a window is `active`
- `start_budget_window`'s description itself changes (built by `build_start_budget_window_tool()`)
  when a window is `pending`, to bias bare replies like "food and drink 125" toward filling in
  the pending window instead of being misread as a purchase

This conditional-tool-list pattern is how ambiguous short replies get routed correctly — if you
add a new stateful flow, follow this pattern rather than trying to disambiguate from text alone.

Full current intent list: `log_purchase`, `start_going_out_session`, `set_going_out_target`,
`end_going_out_session`, `set_spending_tracker`, `get_cycle_summary`, `get_category_status`,
`correct_last_purchase`, `undo_last_purchase`, `start_budget_window`,
`get_budget_window_status`, `cancel_budget_window`, `add_budget_window_category_limit`,
`set_paycheck_period_limit`, `acknowledge_no_spend`, `greet`.

## Tone

- No emojis, ever. No em dashes, ever (periods or commas instead) — this applies to hardcoded
  strings AND the LLM-generated going-out check-in messages (there's an explicit instruction
  for it in that prompt).
- Setup confirmations (starting a session/tracker/window, setting a target/limit) open with a
  random casual or Iron-Man-JARVIS line — see `CASUAL_OPENERS` / `casual_opener()`. Mix of
  "sure bro" / "you got it brotha" and "initiating budget protocol, sir".
- Profanity (`overspend_tail()`) is appended **only** when something is actually over a
  budget/target/cap — never otherwise. Keep these two tone systems separate; don't let cussing
  leak into routine confirmations or casualness leak into overspend warnings.

## Known infrastructure gotchas (don't re-debug these)

1. **API Gateway → Lambda auth**: a bare Lambda resource-based policy
   (`aws lambda add-permission --principal apigateway.amazonaws.com`) does NOT work in this AWS
   account/environment — returns 500 `API_CONFIGURATION_ERROR`. Fix: create an IAM role
   (`jarvis-apigateway-invoke-role` / `jarvis-scheduler-invoke-role`) and set it as the
   integration's `--credentials-arn`. Already implemented in `setup_api_gateway.sh` and
   `setup_session_scheduler_schedule.sh` — if you ever rebuild an integration from scratch,
   skip straight to the IAM-role approach.
2. **Migration idempotency** — see "Deploying changes" above.

## Subagents

`.claude/agents/` has four configs: `schema-agent` (Postgres/migrations), `lambda-builder`
(Lambda code/deploy), `telegram-integration` (webhook/Telegram API specifics), `code-reviewer`
(read-only review). They were written but never actually invoked in the session that built most
of this — the harness only loads agent definitions at session start, so they weren't loadable
mid-session. They should work normally in any fresh session. Prefer delegating schema/Lambda/
Telegram-specific work to them per their descriptions rather than doing everything inline.

## Ideas for continuing (not committed to, just surfaced in chat)

- Build an eval harness for `classify_message` — labeled example messages → expected tool/fields,
  track precision/recall per intent. Highest-leverage next step given how much intent surface
  now exists.
- Log token usage/cost per Claude call; try prompt caching on the (static, repeated-every-call)
  tool definitions.
- Log raw Claude responses alongside classification outcomes for debugging misclassifications
  after the fact.
- A genuine multi-step agentic loop (e.g. "give me a spending review for the week" synthesizing
  across several tool calls) rather than single-shot classification.
- Real conversation memory (pass recent message history to Claude) as an alternative to the
  hand-rolled DB state flags (`awaiting_target`, `window_pending`) — tradeoff exercise between
  explicit state machines and implicit conversational memory.
- Semantic search over past transactions (embeddings + similarity search) — a small real RAG
  exercise.
- Phase 6 from the original spec (optional companion dashboard) was never started.
